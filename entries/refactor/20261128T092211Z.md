### Lessons
- **A safety valve is as wide as the reader's idea of "unparseable".** `vendor_entry_in_use` keeps an entry whenever a lock could not be parsed. Each reader decides what that means, and the pnpm one asks only for a `lockfileVersion:` line. To find the next one, list the readers that can answer "the dependency left the lock" (the npm family and Python, per CLI `commands/vendor.rs` line 530) and give each a file its tool rejects or repairs.
- **Ask the package manager what it does with the conflicted lock.** Yarn 1 and pnpm both resolve lockfile conflicts on `install`. So a conflicted lock is a state the project installs from, and the patched build is what comes out unless something unwired it first. That turns "a confusing message mid-merge" into a lost patch.
- **A real merge places the conflict where the dependency sorts.** `kleur` sorts before `left-pad` and `ms`, so everything vendored fell after the marker. A neighbour that sorts after them would have shown nothing. Use one of each, or place the hunk by hand as the issue's table does.
- **One fixture service serves any project with the same manifest.** The npm and Bun projects reused the Yarn project's service and uuids; only the lock differs.
- **Two guards blocked commands here and are deliberate.** Fetching Yarn Berry from the npm registry to run it was refused (the sandbox note already says so), so Berry is not checked. `rm -rf $VAR/…` is refused; write `"${VAR:?}"/…`.
