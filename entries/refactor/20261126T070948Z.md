**#647, confirmed on `main`, in a narrower and a wider form than the issue says.** Two local servers: one answers 401 to everything (the API refusing a token), one is the public proxy with a free patch. `SOCKET_API_TOKEN`, `SOCKET_ORG_SLUG`, `SOCKET_API_URL` and `SOCKET_PROXY_URL` point at them.

| Command | Requests | Result with the refused token |
|---|---|---|
| `scan --json` | API batch, then proxy batch | "falling back to public patch API proxy (free patches only)", exit 0 |
| `get <uuid>` | API view, then proxy view | the same warning, exit 0 |
| `show <uuid>`, `show CVE-…` | API, then proxy | the patch is shown, exit 0 |
| `get CVE-…`, `get GHSA-…`, `get <purl>`, `get left-pad` | API only | `patch_fetch_failed`: "Unauthorized: Invalid API token", exit 1 |
| `vendor --dry-run` over a hosted pin (the eject) | API view only | `eject_refused`, exit 1. With no token: "Would eject …", exit 0 |
| `apply` with the blob not on disk | API blob only | "Failed to download 1 blob … Unauthorized", exit 1. With no token: patched, exit 0 |
| `repair` | API blob only | exit 1 |
| `rollback` with the before-blob not on disk | API blob only | exit 1. With no token: rolled back, exit 0 |

Two rows contradict what is written down. `CLI_CONTRACT.md` says the eject fetches each record with "the same client and public-proxy fallback as `get`", and it has none. The contract's `show` section says an identifier "is searched like `get`'s" and that the search follows the 401 / 403 rule; `show` does, and `get`'s own search does not, so the same CVE is found by `show` and refused by `get`. For the blob downloads of `apply`, `repair` and `rollback` the contract promises nothing, and the error they print is true. A fix would give `get`'s searches and the eject the one fallback the other four callers have (as `show`'s `Connection::ask` does it), and leave the blob downloads for the issue to decide.
