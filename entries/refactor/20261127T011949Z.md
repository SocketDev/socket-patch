### Leads and issues

**New: L42, filed as #2299.** An agent-mode `scan` or `get` that replaces a recorded patch with a newer one writes the new record into the manifest and then applies. When the apply cannot finish, the record stays replaced: the files hold the old patch's bytes, and the manifest no longer says so. The old patch's after-blob is then the only proof that those bytes are a Socket patch's output, no record references it, and the next cleanup deletes it.

```
$ socket-patch scan --mode agent --prune          # the newer patch's blob answers 500 once
  [update] pkg:npm/lodash@4.17.20 (replacing aaaaaaaa)
Failed to download 1 blob: …
Error: Some patches could not be applied.
GC: pruned 0 manifest entries and removed 1 orphan file (42 B).              (exit 1)

$ socket-patch scan --mode agent --prune          # the API is healthy from here on
Error: Failed to patch pkg:npm/lodash@4.17.20: Cannot apply patch: package/index.js - File hash does not match expected value   (exit 1)
$ socket-patch apply                              (exit 1, the same error)
$ socket-patch apply --check
Run `socket-patch apply` to regenerate them.                                 (exit 1)
$ socket-patch rollback lodash
A file that holds neither content was edited, or is another build's; nothing here can restore it:   (exit 1)
```

`apply --force` or a reinstall is the way out, and `scan`, `apply` and `apply --check` name neither. The same end state follows from:
- `scan --strict` (always, for a newer patch that changes the same files), then `apply --strict`, `repair`, `apply`;
- `get <new uuid> --save-only`, `repair`, `apply`, where no command fails before the `apply`;
- `scan` over a project whose `.socket/blobs/` is not stored.

A plain retry recovers while the old blob is still stored. A failed view of the newer patch keeps the old record, and so does a newer patch that drops a file when the old one cannot be rolled back (`replaced_patch_not_restored`): that is the outcome `CLI_CONTRACT.md` describes for a replacement that cannot go through.

The cause is the order in `download_and_apply_patches_into` (CLI `agent_download.rs`: the record at line 2423, the manifest write at 2431, the nested apply at 2504), which `get.rs` repeats for `get <uuid>` (lines 2262 and 2384; #1835 is open for that copy). #2119 fixed this class for the files a newer patch drops, and its commit message leaves the rest: "a replacement that drops no file behaves as before". Two tests added beside that fix's suite (`tests/in_process_agent_patch_replace.rs`) fail on `main`; the issue has them, and `strict_replacement_applies_the_new_patch_to_the_shared_file` passes beside them because its newer patch drops a file.

The contract documents the pruned-blob case for a user who pruned ("Only a stored blob proves this … `apply --force` is the explicit way to replace it"). So a teammate who pulls a committed upgrade and its prune onto a tree that still holds the old patch gets the same refusal from `apply`: that half is the documented behavior, and it is not part of the issue.

### Lessons
- **Look at what a failed run leaves, then run the next three commands a user would.** The 88 failure runs all reported the failure correctly. The defect was in the state after one of them, and showed only when `apply --check`, `rollback` and `repair` ran next. Follow the advice each command prints, too: here it led from a recoverable state to a stuck one.
- **A fix's commit message names the half it left.** `git log -S` for the refusal code found #2119, and its message says which branch "behaves as before". The suite it added had the harness for a failing test in the other branch in ten lines.
- **Failure rules for the stand-in API** (the 22:56Z entry of 2026-11-26 has `mkrepo.py` and `api.py`). Put the first block before `class H` and the second inside it, and add `if self.fail(): return` after `self.note(…)` in `do_POST` and `do_GET`. The server re-reads `$RULES` when the file changes: `[{"sub": "/blob/", "act": "500", "n": 1}]` fails the first blob request.

```python
import os, time
RULES = os.environ.get("RULES"); _st = {"mtime": None, "rules": [], "left": []}
def pick(method, path):
    if not RULES or not os.path.exists(RULES): return None
    m = os.stat(RULES).st_mtime_ns
    if m != _st["mtime"]:
        _st.update(mtime=m, rules=json.load(open(RULES))); _st["left"] = [r.get("n", -1) for r in _st["rules"]]
    for i, r in enumerate(_st["rules"]):
        if r.get("m", method) == method and r["sub"] in path and _st["left"][i] != 0:
            if _st["left"][i] > 0: _st["left"][i] -= 1
            return r
```
