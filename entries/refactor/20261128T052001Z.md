The 64 MiB row is the size limit (`MAX_TOTAL_DECOMPRESSED_BYTES`, line 20). Both functions bound the gzip stream with `take(limit)`. The limit is a multiple of the tar block size, so it can fall between two entries, and there the tar parser takes the end of its input for the end of the archive. A twin of the unit test `shadowed_member_judges_only_the_listed_files` fails on `main`:

```
boundary at the cap: shadowed_member = Ok(None); read_archive_bytes_to_map = Ok((7, Some("patched")))
boundary one block before the cap: shadowed_member = Err("archive I/O error: unexpected EOF during skip"); …
control: 48 MiB of padding: shadowed_member = Ok(Some("index.js")); read_archive_bytes_to_map = Ok((7, Some("original")))
```

Every other bounded read in core takes one byte more than its limit and fails when it gets it (the wheel reader in `vendor/verify.rs`, line 801, and more than a dozen `take(MAX + 1)` sites). Three tar sites take exactly the limit: these two and `walk_tar_gz` (core `vendor/registry_fetch.rs`, line 1272, at 512 MiB).

`tgz_bytes_match_after_hashes` (core `vendor/npm_common.rs`, line 566) maps any reader error to `false`. Packages over 67.1 MB unpacked exist and have advisories: `next@13.5.6` (72.3 MB), `next@14.2.3` (86.2 MB), `next@15.1.0` (120.6 MB), `aws-sdk@2.1692.0` (98.2 MB), `plotly.js@2.25.2` (86.8 MB), from `npm view <pkg> dist.unpackedSize`. ### Lessons
- **Ask each limit what it does at the limit, not past it.** One block before the limit the reader fails and one block past it fails; exactly at it the archive ends early and everything looks right. `take(limit)` over a stream of fixed-size records has that hole wherever the limit is a multiple of the record size. The idiom the rest of the code uses, `take(limit + 1)` and a check, has none: `grep -rn '\.take(MAX_'` lists the sites, and the ones without `+ 1` are the leads.
- **A check that models an installer has to stop where the installer stops.** The comment on `shadowed_member` lists three things installers do that the decoder does not. Each thing the decoder stops at (a size limit, a zero block, the end of a gzip member) is a fourth, fifth and sixth. For any "what gets installed" check, list where the reader stops and install a file that continues past each stop with every package manager on the machine. It took ten minutes: four tarballs, four installers, `require()`.
- **npm's tar refuses a tarball that inflates more than 1000:1** (`TAR_ABORT: max decompression ratio exceeded`). Padding made of zeros trips it. Thirty-two random bytes in every 4 KiB compress about 100:1 and pass.
- **Yarn 1 reads past the tar end-of-archive marker and into a second gzip member; npm 10.9, pnpm 10.28 and Bun 1.4 do not.** Any reader here that judges a tarball for Yarn 1 has to read on as well.
- **A limit's comment says what it was written for.** "Real socket-patch archives are tiny" sits above a limit that now reads whole packages. `git log -S` on the constant and on its newest caller gave the two PRs between which the meaning changed.
- **The fixture service builds its package from an installed copy** when the project has one under `node_modules/`. Five 14 MiB files there make a served tarball over the limit; no network and no real large package is needed. Stop the holder test before the last quoted run: a stopped service turns every later `vendor` into a connection error.
- **`npm view <pkg> dist.unpackedSize dist.fileCount`** answers "does a real package reach this" in a second. The npm registry is reachable from this sandbox; the public patch API is not.
- A loop that prints `$?` after a pipe prints the status of the pipe's last command. Use `${PIPESTATUS[0]}`, or do not quote the status.
