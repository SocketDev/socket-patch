**New: L54, filed as #2317.** For a Bundler project with no bundle path of its own, and for `-g`, the gem directories come from `gem env gemdir` and `gem env gempath`. The `gem` command applies two gemrc keys to its own paths, `gemhome` and `gempath` (`gem help env` documents `:gempath:`). Ruby and Bundler never read them: `require`, `bundle install` and `bundle exec` use `Gem.dir` and `Gem.path` as the environment gives them. ### Lessons
- **`gem env` is the `gem` command's view, not Ruby's.** A probe that asks a tool's CLI gets the CLI's configuration. For RubyGems the two differ by the gemrc; `--norc` removes it. Before trusting a probe, print the same fact from inside the runtime (`ruby -e 'puts Gem.path'`) under the tool's config files, not only its environment variables.
- **The earlier runs moved the environment; this one moved a config file.** #2312 and #2314 came from variables. A tool's rc file is the other input a probe inherits.
- **A wet `-g` run reaches every copy on the machine.** My PyPI catalog still held `six` 1.16.0, which is the OS Python's version, and the global run patched `/usr/lib/python3/dist-packages/six.py`. I rolled it back and `dpkg --verify python3-six` passes. Take every package the OS ships out of the catalog before a wet global run, or pick one the machine does not have (`find / -xdev -path '*<name>*'` first).
- **As root, two tools write outside `HOME`.** `yarn global add` installs under `/usr/local/share/.config/yarn/global`, and a `bundle install` with no path installs into the Ruby install's own gem directory. I removed both (`yarn global remove`, `gem uninstall -i <dir>`) and checked the directories.
- **A confound from an earlier fixture.** A `multi_json` left in the user gem directory by the global test was patched by the next project's control scan and joined its manifest. Give each test a home of its own.
- **`rm -rf "$P/$d"` is refused here**, as the last entry said of a function. Copy the original files back over the patched ones to simulate a fresh install.
