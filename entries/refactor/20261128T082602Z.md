### Lessons
- **A reader that models "what the build loads" has to be asked of every tool that reads the file, not the one its comment names.** The jar reader's comment is true of `java.util.zip.ZipFile`. Six of seven readers agree with it, and the seventh is the one that makes uber jars. The matrix took fifteen minutes: Python's `zipfile` writes a name twice (with a warning), and `mvn` and `gradle` are on this machine.
- **The `zip` crate's writer refuses a repeated name.** For a Rust fixture, write the second entry under a twin of the same length and rename it in the bytes, in the local header and in the central directory (the test in #2332).
- **A JVM tree's hashes form a chain**: the jar, its `.sha1`, the tree marker `socket-patch.vendor.json` (a sha256 of each file), then the ledger's `jvm_vendor_tree` rows (a sha256 of each file, the marker among them) and `gradle-index.tsv`. To stand in for a commit that replaces the jar, replace each changed file's old digests with its new ones everywhere, and repeat against the previous pass until nothing changes. Comparing with the first snapshot leaves the marker's row stale.
- **A mutant at the call site asks a different question from one in the function.** Most gates here have a unit test of the function. Skipping the call found the one whose caller nothing tests.
- **"No test names the code" is a weak signal.** A script listed 67 contract codes that no test names by literal or constant. `vendor_artifact_non_canonical` looked untested by `grep` and has a test, which asserts through a helper. `vendor_lock_pin_mismatch` was on the list and is the real one. Use the list to choose mutants, not to file.
- **A survivor of the suites you picked is a lead.** Mutants 8 and 28 each passed the first selection and were caught by a suite outside it (the CLI's own unit tests, `apply`). Sweep every target whose source names the ecosystem, then rerun the red ones with no mutant to subtract the root-sandbox failures. A sweep over all 219 targets is too slow here: the suites with a real Go or JVM build take minutes each.
- **A real Maven run changes what core's unit tests see.** See "Seen and not filed". After any probe that runs `mvn`, list what it fetched (`ls -t ~/.m2/repository/org/apache/commons/*`) and remove it, or run core's tests with `MAVEN_REPO_LOCAL` pointed at an empty directory.
- **`rustc` takes 9 GB for core's unit tests.** Building them while a suite sweep ran got a process killed for memory. Build, then run.
- **`cargo test` holds the build lock only while it compiles**, and each integration test is its own target: a probe added to one test file builds and runs in seconds while a long run over other targets continues. Editing a source file of core in that time does not: the next `cargo test` rebuilds everything, so run the built test binaries directly (from the package directory, with `CARGO_MANIFEST_DIR` set).
- Java prints `Picked up JAVA_TOOL_OPTIONS` on every call here: send stderr to `/dev/null` when quoting output.
- The hunt took about 90 minutes of wall time: the first sixteen mutants 30 (two builds of 4 and 3 minutes), the jar matrix and its CLI probe 20, the other fourteen and the sweeps 35.
