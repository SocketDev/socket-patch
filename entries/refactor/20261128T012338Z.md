**Seen and not filed:**
- **Gradle's exclusive upper bound.** The port rejects a candidate whose parts begin with the bound's parts (`qualifies`). Gradle rejects one whose text begins with the bound's text: the bytecode of `VersionRangeSelector.isLower` in `gradle-dependency-management-8.14.3.jar` is `compare(v1, v2) < 0 && !v1.toString().startsWith(v2.toString())`. The two differ where a candidate spells the bound's numbers with other separators (`[1.0,2.0)` and `2-0+M1`: Gradle admits, the port rejects) or continues the bound's last word (`[1.0,2.0-rc)` and `2.0-rcM1`: Gradle rejects, the port admits). They agree on `2.0-rc1`, `2.0.rc1`, `2.0rc1`, `2.0-SNAPSHOT` and `1.10.0-socket.4d5e6f70` against their own bound (both reject each), which is how published prereleases and the hosted suffix are spelled. No published version I know of has the other spellings, so this is not a problem a project can meet. If the port is touched again, `startsWith` is the rule to copy.
- **The apply summary can count one package twice.** With a symlink inside an installed package that points out of the tree, and a record naming a file through it, `apply` over already-patched bytes prints `0 of 10 targeted patches applied, 2 already patched, 9 failed`. `vex` attests that package from the bytes behind the link. The state is hand-built: `apply` refuses that package, so it cannot write those bytes itself, and an npm tarball holds no links.
- **`apply --force` over a key with backslashes** (`package/..\..\..\outside\victim.txt`) patches the package's other file and skips that one as missing. On Linux the key is a file name, and the skip is the documented `--force` rule.

### Lessons
- **Grep for the rule's verb, not its module.** A grep over core for function names holding `admit`, `satisf`, `version_cmp`, `versions_equal` or `requirement` listed every reader of a version rule in one screen, and the second npm range reader was on it. Searching for the first reader's name had found only its three callers.
- **The reference for a port is the tool's library, and it is already on this machine.** node-semver is in npm's tree (`/opt/node22/lib/node_modules/npm/node_modules/semver`), `packaging` imports in Python, Maven's resolver is `/opt/maven/lib/maven-resolver-util-*.jar` (compile a ten-line class against it and `maven-resolver-api`), Gradle's comparator and selector scheme load in a `build.gradle` task (`org.gradle.api.internal.artifacts.ivyservice.ivyresolve.strategy.*`, `gradle --offline -q --no-daemon`), and RubyGems is `Gem::Version` and `Gem::Requirement`. Each prints one answer per input line.
- **Run the repository's own file without building core.** A scratch crate outside the repository loads a source file by path, so the reader under test is the bytes on `main`, and a build takes seconds instead of four minutes:

```rust
// Cargo.toml: the versions Cargo.lock pins (semver, regex, once_cell, serde_json), and an empty [workspace]
#[path = "/home/user/socket-patch/crates/socket-patch-core/src/utils/npm_range.rs"]
mod npm_range;
mod formats {                       // a module that names its neighbours gets them as stubs
    pub mod text { pub fn strip_bom(s: &str) -> &str { s } }
    pub mod pnpm {
        pub mod modules_yaml { pub fn field(_: &str, _: &str) -> Option<String> { None } }
        #[path = "/home/user/socket-patch/crates/socket-patch-core/src/formats/pnpm/version.rs"]
        pub mod version;
    }
}
// main: read "a\tb" lines from stdin, print "a\tb\t<answer>"; diff against the tool's output
```

  `include!` fails on a file that starts with `//!`; `#[path]` does not. A type in the middle of a large file (the RubyGems port) is its line range written to a file of the scratch crate with `sed`.
- **Take the inputs from real manifests.** The 663 npm ranges came from the `dependencies` of every `package.json` under npm's own tree, each paired with versions built from its own numbers (the same, one up and one down in each place, with and without a prerelease). `^0.0.6` was one of them; my hand-written list would have been called contrived.
- **When a port and its tool differ, read the tool's rule before judging.** `javap -p -c` on `VersionRangeSelector` gave Gradle's rule in a minute, and with it the two kinds of input that differ and the reason no published version is one of them.
- **`intersects` is not `satisfies` for a prerelease.** pnpm intersects an override's selector with the dependency's range. The pnpm reader's `None` for a prerelease looked like a gap and is the right answer, so the fix cannot be "call the other reader" for every input.
- **A lead that is true and small still gets filed, at the end of the queue.** #2324 passes the first gate by its letter. It went in as low priority, and the owner was not notified of it.
- This sandbox has pnpm 10.28.0 and no pnpm 11 or 12, Bazel or conda. The register's sandbox note now says so.
