**New: L53, filed as #2315.** `apply --vex <path>`, `scan --vex <path>` and `vendor --vex <path>` write the document only when the host command succeeds. When it fails they neither write the document nor look at the path, so a document an earlier run wrote there stays, and the run says nothing about it. `docs/usage.md` (line 292) tells users to keep the document at one path ("commit it and regenerate it whenever the patches change"), and `CLI_CONTRACT.md` (line 739) promises that "a pipeline reusing one path can never ship yesterday's attestation for a now-unpatched tree".

```
$ socket-patch apply --vex socket.vex.json --vex-product pkg:generic/app@1          # day 1
Wrote OpenVEX document with 4 statements to socket.vex.json                      (exit 0)
$ # day 2: a fresh install put the registry's files back, and the patches no longer fit them
$ socket-patch apply --vex socket.vex.json --vex-product pkg:generic/app@1
Summary: 0 of 4 targeted patches applied, 0 already patched, 4 failed, 0 not found on disk       (exit 1)
$ cmp socket.vex.json day1.vex.json && echo "identical to day 1's"
identical to day 1's
$ jq -c '.statements[0] | {status, products: [.products[]."@id"]}' socket.vex.json
{"status":"not_affected","products":["pkg:generic/app@1","pkg:npm/lodash@4.17.20"]}
$ socket-patch vex --product pkg:generic/app@1 -O socket.vex.json                   # the standalone command, same tree
Warning: Removed the previous VEX document at socket.vex.json (this run could not attest it).
Error: No applied patches with vulnerability metadata to attest.                 (exit 1)
```

Seven states ran, and each leaves the day 1 document: one of four patches failing and all four failing under `apply`; all four failing under `scan --mode agent`; the originals back with the blobs missing under `apply --offline`; a manifest that does not parse; and an unreachable patch API under `scan --mode agent` and under a hosted `scan` (also with a `socket.yml` that does not parse). `apply --json` reports `status: "partialFailure"` with no `vex` key and no warning. The standalone command in the same state rewrites the document with what verifies (three statements where one patch failed) or removes it.

The cause is the gate in front of each embedded call: `apply.rs` line 2239 (`if success && …`), `scan/mod.rs` lines 439 and 501 (`base_code != 0`), and `vendor.rs` line 1261 (`exit == 0`, read and not run). `generate_vex_with_cleanup` (CLI `commands/vex.rs`, lines 2335 to 2379) is the only caller of `remove_stale_vex_doc`, and the host commands reach it only after they succeed. The class was fixed one path at a time: a failed VEX step in #208 (cea7195d), the manifest-less no-op in #251 (cf8150b1), a truncated document after a failed write in #1262 (c50be524, for #1144). A test that is the twin of `apply_vex_failure_removes_stale_openvex_doc`, with the failure in the apply, fails on `main`; the standalone control passes. The issue has both:


The planned fix is one helper that every host command calls on its failure path: it removes a recognizable OpenVEX document at the path and raises `vex_stale_doc_removed`. The issue names the other fix (write the document from the post-run state after a failed apply too) and asks a maintainer to say so if that is preferred, or if a failed hosted scan that changed nothing should keep the document. ### Lessons
- **"Only on success" is a gate worth running from the failure side.** The cleanup lived inside the step the gate skips. For any output a command writes at the end of a good run, seed yesterday's file, make the command fail, and look at the file. Then run the standalone command over the same tree: the two answers side by side are the evidence.
- **An existing test's doc comment can state the rule its twin breaks.** `apply_vex_failure_removes_stale_openvex_doc` says a pipeline "must not ship yesterday's `not_affected` doc for a tree this run could no longer attest", and fails only the VEX step. Changing which step fails took ten lines.
- **A harness function that deletes its own directory is refused here.** `rm -rf $PROJ` inside a shell function is stopped by the sandbox's safety check. Give every fixture a new directory name and `mkdir` it; nothing needs deleting.
- **The entrypoint command reads the machine.** Its baseline line said `4 project + 311 global packages checked`. Run it with `--dry-run` or `SOCKET_OFFLINE=1` unless the catalog cannot match a real package.
- **Two API variants cover the rollout's edge rules.** `api.py` of the 22:56Z entry of 2026-11-26 with two additions: an env variable whose value, found in a request path, answers 500 (`FAIL_SUBSTR='by-package/pkg:npm/lodash'`), and one that turns `canAccessPaidPatches` to false, beside a catalog whose top patch has `"tier": "paid"`.
- **A server that accepts and never answers** is five lines of Python (`listen`, then `accept` in a loop, keeping each connection). It holds an `apply` inside its lock for a signal test and shows a time limit.
