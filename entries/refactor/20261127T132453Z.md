When it does not (a fresh runner), `scan` says `No packages found. Run your package manager's install first.` with exit 0 and no warning, `apply` over a committed `.socket/` exits 1 with `The targeted manifest patch matched no installed package`, and `apply --check` exits 0 with `0 patches checked; 1 patch not installed, skipped`.

The cause is one function, `m2_repo_in` (core `crawlers/maven_crawler.rs`, lines 694 to 777). It takes `user.home` from `-Duser.home` in `MAVEN_OPTS`, else `$HOME`, where the JVM takes the passwd entry and Maven lets a command-line `-D` move it. It reads `-Dmaven.repo.local` from three sources and drops a relative one without a warning. It reads two settings files. Three things in the tree already know better:

- `GradleHome::resolve` (core `gradle/home.rs`, line 52) takes the passwd home on Unix (#646, 0685ba8c), and `utils::fs::passwd_home` documents it as "what the JVM reports as `user.home`".
- `settings_mirror_sets` (core `crawlers/maven_crawler/settings_mirrors.rs`, line 157), the hosted mirror gate's reader, follows `-s`, `-gs`, the Maven Wrapper's distribution and the `mvn` on `PATH`, and says the launcher has ignored `$MAVEN_HOME` since Maven 3.5.
- The first fix of this lookup (#423, ca6dc059) says Maven "fixes user.home before command-line -D flags in MAVEN_ARGS apply". State 2 shows the opposite, and the unit test `maven_args_user_home_does_not_move_the_m2_directory` pins the wrong claim.

Three unit tests fail on `main`; the issue has them. In the first, one environment goes to both lookups: the Gradle assertion passes and the Maven one fails.

### Lessons
- **The register's tool list was wrong about Go.** `go version` answers `go1.24.7`. Run `command -v` for a tool before writing "needs X"; the list in the notes is what an earlier run saw. A `docker` client is here too, with no daemon.
- **A JVM's home is the passwd entry.** `HOME=<dir> java -XshowSettings:properties -version 2>&1 | grep user.home` prints `/root`. Every Maven run here that did not move the repository wrote `/root/.m2/repository`, whatever `HOME` the harness set. The bench's hosted environments set `HOME` to a directory of their own, so for a JVM tool they are in state 1 already.
- **A stale copy in the default place turns "not found" into "patched the wrong copy".** My first matrix said `Found 1 package` in every state, because the first run had filled `/root/.m2/repository`. The dry run could not tell the two outcomes apart. The test is a wet run and a marker count over every copy, then a rollback.
- **A variable the harness sets can mask the state under test.** My Go runner exported `GOFLAGS=-buildvcs=false`, which replaces the `GOFLAGS` of Go's env file, so the `-modfile` layout looked like a defect until I dropped it. Make the project a real git repository instead (`git init` and one commit).
- **When a rule looks wrong, grep for a second reader of it.** `grep -rn 'global-settings'` found `settings_mirror_sets`, which already follows `-s`, `-gs` and the `mvn` on `PATH`. The fix is then to share it, and the issue can say so.
- **The Maven fixture.** A `pom.xml` with one dependency, `javax.inject:javax.inject:1` (a 2.5 KB jar; Maven Central is reachable, and `mvn` needs the session's `JAVA_TOOL_OPTIONS` passed through `env -i` for the proxy). The catalog entry is `pkg:maven/javax.inject/javax.inject@1` with the file key `package/javax.inject-1.jar`, a whole-jar record: the patched bytes are the jar with one member appended.

  "files": {"package/javax.inject-1.jar": {"before": base64.b64encode(before).decode(), "after": base64.b64encode(after).decode(), "beforeHash": gh(before), "afterHash": gh(after)}}}]}, open(out, "w"))
