## Cells (Linux)
- **Pipenv 11.10.4, hosted, out-of-tree venv:** `scan --mode hosted` writes a **`path`** reference (probe found `pipenv, version 11.10.4` on PATH). `pipenv install --deploy` into an emptied venv gives the PATCHED `six`, and `vex --product` gives `not_affected`. Rollback re-derives the entry from PyPI **byte-exact**. Over a warm venv, `redirect_pypi_stale_install` fires and `vex` omits the patch as `not_applied`. Pass.
- **`SOCKET_PIPENV_MAJOR=11` / `11.10.4`** with no pipenv on PATH: `path`, no warning. With neither set: `file` + `redirect_pipenv_installer_unknown`. Pass (documented).
- **Pipenv 9.1.0, hosted, in-project `.venv`:** `path` ref, `install --deploy` gives PATCHED, rollback succeeds. Pass. Here the 9.1.0 lock had `"hashes": []`, most likely because its old resolver couldn't fetch hashes through the sandbox proxy. Rollback restores the full PyPI hash list instead of `[]`, so it isn't byte-exact, but the restored lock reinstalls upstream fine. Not filed (see Known non-bugs).
- **socket.yml policy, hosted, two-root Pipenv monorepo (2026 shape):** `ignorePaths` (glob and `/apps/b/Pipfile.lock` marker), `includePaths`, `projectIgnorePaths`, `ignorePackages` (purl and bare name, case-insensitive), `ecosystems: [npm]`, `enabled: false`, `minSeverity: critical`, `maxNewPatches: 0` / `1` (a purl admitted in apps/a is free in apps/b, as documented): all pass. A patch that's already hosted is retained when policy later excludes it. `--prune` is a documented no-op in hosted mode.
- **`get` vs socket.yml:** `get <purl>` warns `policy_bypassed`, but **`get <uuid>` doesn't, in agent, hosted or vendored mode** → **filed #453**.
- **Hosted rollback with a mirror / `${PIP_INDEX_URL}` source:** refused, `partial_failure` exit 1, and the error names the source and the `git checkout -- Pipfile.lock` remedy. `https://pypi.org/simple/`, `PyPI.org` and `pypi.python.org` restore byte-exact. Pass (documented). `${PIP_INDEX_URL}` is refused even when the variable is exported as pypi.org: the check doesn't expand env vars. That's conservative and documented ("names a PyPI source in `_meta.sources`"), so I didn't file it.
- **Concurrent hosted scans** (6 parallel, 3 rounds): one or more exit 0, the rest `lock_held` exit 1, the lock is always valid and redirected, and no `.socket/` residue. Pass.
- **Global `-g` on 2023.12.1** (`pipenv install --system --deploy` into a standalone CPython 3.12): `scan -g` / `--json` inside and outside the project reports only `six`. `scan -g --mode hosted` and `--global-prefix … --mode hosted` exit 2 and write nothing. `scan -g --apply` patches the global copy, the lock is untouched, `vex -g` gives `not_affected`, `rollback -g` is byte-exact, and vex afterwards has nothing to attest. `SOCKET_GLOBAL=1 get <uuid>` and `--global-prefix` rollback also pass. Pipenv's WORKON_HOME venv isn't scanned. The 114 pypi packages `-g` counts come from the system interpreter paths (`/usr/lib/python3*`, `/usr/local/lib/python3*`), which is by design.
- **`-g` from inside a hosted / vendored Pipenv project:** `rollback -g` and `remove <purl> -g` unwind the **project's** `Pipfile.lock` (and the vendored artifact), and `get <uuid> -g --mode hosted|vendored` rewires the project's lock, all with exit 0. This is the cross-PM root cause of #436 / #445 (fix PR #446 open), so I commented there with the Pipenv evidence instead of filing: https://github.com/SocketDev/socket-patch/issues/445#issuecomment-5928712996 and https://github.com/SocketDev/socket-patch/issues/436#issuecomment-5928721100
- **macOS / Windows:** blocked. `git push --delete` is still cut off by the git proxy ("unexpected disconnect while reading sideband packet"), so I pushed no probe. `bughunt/pipenv/20260930-venv-discovery` and `bughunt/pipenv/20260930-virtualenv` still need a maintainer to delete them.

## False positives ruled out
- The Pipenv 9.1.0 `"hashes": []` rollback difference: likely a sandbox artifact of the lock, and the restore is a valid, stricter lock.
- The `${PIP_INDEX_URL}` rollback refusal is documented and fail-closed.
- The large `scan -g` counts: by design, `-g` covers every ecosystem and the system Python paths.
