[agent] 2026-09-30: Pipenv bug-hunt run

This is the first run, so the ledger started empty and there were no `pm:pipenv` issues to re-triage.

**Tested:** main `f6b7fb9` (CLI 4.0.0), latest release 4.0.0. The previous release, 3.3.0 (from PyPI), was used for first-bad checks: it has no hosted mode and no Pipenv out-of-tree venv discovery.

**Setup:** patch.socket.dev is blocked by the sandbox proxy (403), so a local mock patch API served a real patched `six-1.16.0` wheel (the same recipe as the Poetry routine). A local HTTP forwarder for pypi.org / files.pythonhosted.org, via `SOCKET_PYPI_JSON_API`, stood in for rustls vs the proxy CA. Every cell ran a real Pipenv release (2018.11.26 and 2022.12.19 on py3.8; 2023.12.1 and 2026.8.0 on py3.12): install / sync / `install --deploy` / lock, then a byte check through `pipenv run python`.

## Cells

- **Agent, stray `venv/` directory:** **fail on every OS and version → #334.**
- **Agent, `.venv` + `PIPENV_VENV_IN_PROJECT=0`:** **fail on 2023.12.1 and 2026.8.0 on every OS → #334.** Correct on 2018 and 2022, which read "0" as truthy.

- **Hosted, Linux 2026.8.0:** `default` + `develop` + named category `tests` all rewritten; `pipenv sync --categories "packages tests"` into a fresh venv gives PATCHED; `install --deploy` exits 0; the stale-install warning fires with in-project and out-of-tree venvs; rollback is byte-exact. All pass.
- **Hosted, live-lock conflict (file dep) + sibling requirements.txt:** **fail on Linux 2018 / 2022 / 2023 / 2026 and on macOS and Windows 2023 / 2026 → #333.**
- **Hosted, stray `venv/`:** stale-install warning suppressed (part of #334).
- **Mode switch, hosted ⇄ vendored, installed and lock-only:** fail (same root cause as #328). Commented there with the Pipenv evidence.
- **Vendored, Linux 2026.8.0:** vendor from a lock-only checkout (pristine wheel fetched by lock digest), `pipenv sync` gives PATCHED; `repair` after deleting the committed wheel, both with the venv and lock-only, rebuilds a byte-identical wheel. Pass. The Poetry lock-only repair bug does **not** reproduce on Pipenv, because Pipfile.lock keeps every release digest.

## False positives ruled out

- Pipenv 2026.8.0 crashes (`'str' object has no attribute 'expanduser'`) when `WORKON_HOME` contains `$HOME`. That's Pipenv's own bug, not socket-patch's.
- `vendor_fetch_failed` against pypi.org is a sandbox TLS artifact; use a local forwarder via `SOCKET_PYPI_JSON_API`.
- `rollback` removing manifest entries is documented (README `rollback`).
- `vex` correctly refuses (`no_applicable_patches`) in the #333 half-redirect case, so there is no false attestation.
