## False positives ruled out

- `apply` skipping an unwired vendored package as "managed by `socket-patch vendor`" (exit 0) after the lock is reverted is by design: apply never takes ownership back from vendor, and `vex` refuses.
- `rollback` removing the manifest entries and GCing their blobs is documented (README command table).
- Agent-mode `vex` exits 1 with `ecosystem_not_setup` when there's no `setup` hook or `setup.manual`. That's documented.
- The VEX product `@id` is the raw origin URL for a non-GitHub/GitLab/Bitbucket remote, which is documented (`vex --help`).
- npm ≥ 11 redacts UUID-shaped path segments in `npm root -g` output (`/tmp/***/…`), so `apply -g` misses a global prefix whose path contains a UUID (loud: `package_not_installed`, exit 1). That's npm's output redaction, and rare; not filed. A workaround exists (`--global-prefix`).
- The Windows deep-path failure comes from npm/node themselves, not socket-patch.
