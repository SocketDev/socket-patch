[agent] 2026-10-02: handover from the Bun bug-hunt routine (#306). Not filed: the behaviour lives in the shared npm-family VEX discovery and reproduces identically with npm 10, so it isn't Bun-specific. It might also be by design, since CLI_CONTRACT's vendored row attests from "the committed artifact + lock wiring".

**Observation:** a vendored (and, under `--no-verify`, a hosted) `vex` attests `not_affected` for `name@version` when the lockfile wires one copy of it to the Socket artifact and a second, plain **registry** entry of the same `name@version` in the **same** lockfile is left unwired. That second copy installs unpatched. `contest_across_locks` (`vex/discover/mod.rs:574`) and `push_uncontested` (`vex/discover/npm.rs:99`, `*j != i`) only contest refs across *different* locks. #325 / #326 / #497 handle bundled and non-registry copies in the same lock, but not an unwired registry copy.

**A natural way to get there:** run vendored (or hosted) scan, then add a workspace member that depends on the same `name@version` and run `npm install` / `bun install`. The package manager resolves the new nested copy from the registry. Re-running `scan` heals it (verified), but in between `vex` attests.

Repro (main `61cfb9b`, Linux, 2/2 runs each, local mock API; the patch is for `pkg:npm/is-number@6.0.0`):
```sh
# root: is-number@7.0.0, workspaces packages/*; packages/a: is-number@6.0.0
npm install && socket-patch scan --mode vendored --yes        # packages/a/node_modules/is-number → file:.socket/vendor/…
# add packages/b with is-number@6.0.0
npm install                                                    # packages/b/node_modules/is-number → registry 6.0.0 (unpatched bytes)
socket-patch vex --json --product pkg:npm/app@1.0.0 -O vex.json   # verified pkg:npm/is-number@6.0.0 (also with --no-verify)
```
Bun (1.4.2, text v2 workspace lock): the same with `c/is-number: ["is-number@6.0.0", "", {}, …]` beside the rewired entries. Vendored `vex` (default and `--no-verify`) attests. Hosted default `vex` correctly skips it (it hashes the installed copies), but hosted `vex --no-verify` attests. Bun 1.1.45 `bun.lockb`: hosted default skips, which is correct.

**Expected (suggestion):** treat an unwired registry entry of the same `name@version` in the same lock like the #326 non-registry case: no attestation, plus a diag ("re-run scan to rewire every copy").
