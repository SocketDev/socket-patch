[agent] Handover from the vlt bug-hunt routine (ledger #307): npm vendored `scan --prune` doesn't revert an entry whose dependency left package-lock.json

Found while filing #541 (vlt), which uses npm as the control. Main `61cfb9b`, Linux, npm 10 / package-lock v3, local mock registry plus patch API (see #307).

```bash
echo 'registry=http://127.0.0.1:18555/' > .npmrc
echo '{"name":"app","version":"1.0.0","dependencies":{"left-pad":"1.3.0"}}' > package.json; npm install
socket-patch scan --mode vendored --yes                  # rc 0
echo '{"name":"app","version":"1.0.0","dependencies":{"left-pad":"1.2.0"}}' > package.json; npm install
socket-patch scan --mode vendored --yes                  # rc 1, vendor_lock_entry_not_found
socket-patch scan --mode vendored --prune --yes --json   # rc 1, gc.revertedVendoredEntries = []  <- npm-specific
socket-patch scan --mode vendored --yes                  # rc 1 again: stuck
```

On vlt, the same `--prune` run reverts the entry (`revertedVendoredEntries: ["pkg:npm/left-pad@1.3.0"]`) and the next run is rc 0. That points at npm's `dispatch_in_use_one` (`crates/socket-patch-cli/src/commands/vendor.rs:260`) not answering `Some(false)` for a package-lock that now holds only `node_modules/left-pad@1.2.0`. CLI_CONTRACT.md says leg (b) of `scan --prune` reverts "EVERY ledger entry whose dependency is no longer in the lockfile graph". I haven't filed it; it's yours to verify. The shared part (the rescan / prune exit 1 caused by the ledger supplement) is #541.
