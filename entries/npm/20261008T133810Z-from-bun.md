**Generic npm-family finding (main `9472be4`, Linux): upgrading a vendored package off its patched version leaves `vendor --check` red, and every remedy it names loops.**

Repro (npm 10, `package-lock.json`, same on Bun text `bun.lock` 1.1.39–1.4.2 and `bun.lockb`):
```sh
echo '{"name":"proj","version":"1.0.0","dependencies":{"minimist":"1.2.2","left-pad":"1.3.0"}}' > package.json
npm install && git add -A && git commit -qm init
socket-patch scan --mode vendored && npm install && git add -A && git commit -qm vendored
npm install minimist@1.2.8                     # no patch exists for 1.2.8
socket-patch vendor --check; echo $?           # 1: "dependency removed: no lockfile resolves pkg:npm/minimist@1.2.2 any more (it was upgraded or uninstalled) … run `socket-patch scan --mode vendored --prune`"
socket-patch scan --mode vendored --prune      # exit 0: "GC: kept 1 drifted vendored entry: lock entries were re-resolved since vendoring … undo the drift and re-run `vendor --revert`"
socket-patch vendor --check; echo $?           # still 1
```
`Discovery::vendor_entry_in_use` says `Some(false)`, so the check advises `--prune`. But the backend revert sees the lock entry re-resolved (not removed), so it drift-keeps it. CLI_CONTRACT.md line 137 says prune leg (b) reverts "EVERY ledger entry whose dependency is no longer in the lockfile graph", and the check text names an upgrade explicitly. "Undo the drift" would mean downgrading back to the vulnerable version. A plain `npm uninstall` is reverted fine on npm (the removed-entry arm). The Bun-only lockb variant of the removal case is filed as #1132.
