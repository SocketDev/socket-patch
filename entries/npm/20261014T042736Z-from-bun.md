**A root `scan --mode vendored` exits 1 (`partialFailure`) on a nested independent project's packages, while hosted mode only warns.** This is generic to the npm family. I reproduced it on npm 10 (Node 22) and on Bun 1.3.0 / 1.3.9 / 1.4.3, socket-patch `bb73e2f`, 2/2.

Shape: the repo root is a project with its own lock. `tools/x/` is an independent project (not a workspace member, or a Bun `!`-excluded member) with its own lock and `node_modules`, and depends on a patched package that the root doesn't have.

```sh
mkdir -p r/tools/x && cd r && git init -q && echo node_modules/ > .gitignore
echo '{"name":"root","private":true,"dependencies":{"minimist":"1.2.5"}}' > package.json
echo '{"name":"x","private":true,"dependencies":{"left-pad":"1.3.0"}}' > tools/x/package.json
npm install && (cd tools/x && npm install)
socket-patch scan --mode vendored --json   # partialFailure, exit 1: left-pad "downloaded" then failed vendor_lock_entry_not_found ("package-lock.json has no registry entry for left-pad@1.3.0")
socket-patch scan --mode hosted --json     # success, exit 0: left-pad skipped (redirect_*_entry_not_found / redirect_unconfirmed)
```

The crawl picks up `tools/x/node_modules`, and vendored mode then tries to wire that package into the root lock. Hosted documents this shape as a warning (run the nested project by PATH), but vendored turns it into a permanent exit 1 on every root run, and `bun install` / `npm install` doesn't clear it. I haven't filed it. It's yours to judge, for example against how the agent-mode nested-project rules in docs/configuration.md work.
