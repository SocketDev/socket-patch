**Filed**
- #423: Maven's local repository is resolved as `$MAVEN_REPO_LOCAL` → **`$M2_HOME/repository`** → `~/.m2/repository`. `settings.xml` `<localRepository>` is ignored, and on Windows `HOME` wins over `USERPROFILE`. With any of these triggers, `scan -g` / agent scan report `scannedPackages: 0` and exit 0, and **`rollback -g` exits 0 `package_not_installed`, drops the manifest entry and GCs the blob while `~/.m2` stays patched**. `apply -g` correctly exits 1. Reproduced on Linux / macOS / Windows × 3.6.3 / 3.9.11 / 4.0.0-rc-7 (probe), plus 3.8.8 on Linux. Not a v5 regression: 4.0.0 already behaves this way.
- #424: `scan --mode agent --json` / `get --json` drop the nested apply failure: exit 1 and `partial_failure`, but `failed: 0`, the patch shows `action: "added"`, and there's no error text (found with a read-only global `~/.m2` as user `nobody`). The human output and the standalone `apply --json` do report `Permission denied`. Code: `get.rs:2469` keeps only a bool. Probably affects every ecosystem.
- #430: v5 reactor vendoring with `--maven-config=none` writes no `.mvn/`, so a fresh checkout fails `mvn -o` (no `aether.offline.protocols=file`) on 3.9.11 and 4.0.0-rc-7. On 3.9.11, `cd a` / `-f a/pom.xml` also fail, because `${maven.multiModuleProjectDirectory}` resolves to the module. The failure is loud, not silent. `auto` passes the same capstone.
