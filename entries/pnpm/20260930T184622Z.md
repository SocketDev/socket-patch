Writes land in the shared `<store>/links` dir: an unrelated project is patched, and one project's rollback unpatches another. Fails on Linux with pnpm 10.12.1–12.8.1, and on the macOS and Windows probe with pnpm 11.27.0 and 12.8.1. Releases 3.3.0 and 4.0.0 behave the same.
- **fail #362**: agent `apply` on a transitive dep with a custom `virtualStoreDir` (pnpm 8–12) or the global virtual store (10.12+) is reported `package_not_installed`. Fails on Linux, macOS and Windows.
- **fail #360**: vendored mode on pnpm 10.5.2, 10.12.1 and 10.34.5 with user `overrides:` in pnpm-workspace.yaml. `vendor` succeeds, then a fresh `--frozen-lockfile` install fails with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`, and a re-lock drops the user's overrides. Passes on 10.0.0, 11.27.0 and 12.8.1. Release 4.0.0 has the same bug.
- pass: vendored lifecycle on pnpm 10.34.5 and 11.27.0 (vendor → fresh frozen `--offline` install → vex → revert). Also passes with `nodeLinker: hoisted` and with a flow `packages: ['.']` plus `catalog: {…}`.
- pass: agent `apply` / `rollback` with `nodeLinker: hoisted` (pnpm 11.27.0). The CAS file is not written through.
- pass: hosted `scan --mode hosted` on pnpm 11.27.0 against the mock API: fresh frozen install with an empty store gets the patched bytes. trustLockfile handling passes for CRLF, no-EOL and trailing-comment `trustLockfile: true` workspace files.
- fail, not filed (queued in the backlog): hosted trustLockfile append and vendored overrides append on a *whole-document flow* `pnpm-workspace.yaml` (`{packages: [.]}`) or a file ending in `...`. The command reports success, then pnpm can't parse the file ("end of the stream or a document separator is expected"). Reproduced on pnpm 11.27.0.
- refused, as designed: vendored with a CRLF `pnpm-workspace.yaml` or `pnpm-lock.yaml` (`vendor_lockfile_crlf_unsupported`), a BOM package.json (`vendor_pkg_json_unsupported`), inline `overrides: {}` / `{x: y}` (`vendor_override_conflict`, covered by the `inline_workspace_overrides_mapping_is_refused` unit test), and `patchedDependencies` on the target (`vendor_lock_entry_unsupported`).

### False positives ruled out
- Vendored `vex` attesting `not_affected` in a fresh clone whose install failed is by design: vendored VEX stands on the committed artifact plus lock wiring (CLI_CONTRACT "Manifest-less VEX"; `vendored_tree_out_of_sync` is a warning only).
- The global virtual store "not reproducing" with pnpm 10.34.5 on GH runners is expected: pnpm 10 disables it when `CI` is set. pnpm 11+ keeps it.
- `vex --output /dev/stdout` hangs when stdout is a pipe. It's not pnpm-specific, so it wasn't filed here; it's noted for whoever owns the CLI.
