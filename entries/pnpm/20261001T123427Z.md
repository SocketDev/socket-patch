- **New shape: pnpm 12 two-document lock.** pnpm 12.8.1 writes `pnpm-lock.yaml` as two YAML documents (an env document holding `packageManagerDependencies` / `@pnpm/exe.*`, then the project lock) whenever `package.json` has `packageManager`. pnpm 11.28.3 and 10.34.5 write a single document for the same input.
  - pass: hosted `scan --mode hosted` pins the entry in document 2. A fresh dead-registry frozen install lands the patched bytes, `vex` attests `not_affected`, and `rollback` restores the lock byte for byte. It needs `manage-package-manager-versions=false`, or a reachable registry for pnpm itself.
  - **fail #466 (new)**: vendored on the two-doc lock refuses with `vendor_lock_entry_not_found`. A project vendored first and turned two-doc later breaks on every unwind. `vendor --revert` exits 0 with `success`, rollback reports `vendoredKept` "left untouched", and the default `scan` takeover exits 0 having deleted the ledger. All three leave 5 `file:.socket/vendor` refs, so the next frozen install fails with `ERR_PNPM_OUTDATED_LOCKFILE`. Root cause: `section_bounds` takes the first `packages:` / `importers:` header. Reproduced 2/2, and the single-doc control passes. https://github.com/SocketDev/socket-patch/issues/466

### False positives ruled out
- Hosted on pnpm 9 plus an existing `node_modules`: the frozen install keeps the upstream bytes. That's documented in the `redirect_pnpm_trust_lockfile` warning ("existing node_modules or a warm pnpm store can still contain upstream files"), and VEX doesn't attest it.
- 4.0.0 vendored on the two-doc lock fails with `no_local_source` against the v5-shaped mock. That's a mock incompatibility, so it can't be used for a bisect.
- pnpm 12 warns `The "pnpm" field in package.json is no longer read … pnpm.overrides` on vendored projects. The workspace-file override is what takes effect, so this is noise only. Noted on #466.
