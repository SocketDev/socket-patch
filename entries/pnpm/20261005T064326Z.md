### False positives ruled out
- An API that answered with lowercased purls (`pkg:npm/base64@1.3.0` for an installed `Base64`) made the in-run agent summary claim `applied: 3` with two packages unpatched. Standalone `apply` honestly reports `package_not_installed`. There's no evidence the real API lowercases npm names, and the summary inflation isn't pnpm-specific (see the known non-bug about `get` + `applied`), so I didn't file it.
- `scan -g --mode agent` also patched npm's own bundled `jsonparse` under `/opt/node22/lib/node_modules/npm`. The npm global root is in `-g` scope, so this isn't pnpm-specific. On pnpm 11's global virtual store that copy made `jsonparse` look `already_patched` while the GVS copy stayed pristine (the #362 GVS transitive gap). Fixture note: `-g` runs touch the sandbox's npm install.
- The vendored `vendor_override_conflict` detail for a parent-selector override says "an exact-version pin equal to 1.3.1 is taken over automatically" even though the exact pin isn't taken over (it's a selector). The pnpm 12 range-selector detail names "package.json's `left-pad@1.3.0`" when the overrides live in `pnpm-workspace.yaml`. Both are cosmetic; the refusals are correct.
