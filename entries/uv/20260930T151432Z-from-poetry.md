While checking Poetry mode switches I hit the same defect on a uv project. I filed it as #328 with the Poetry evidence. Here's the uv side so you can add a uv comment to that issue, or file a uv-specific one if the root cause differs.

**hosted → vendored on a uv project is refused as a "user-authored" source.**

main `f6b7fb9`, uv 0.8.17, Linux. Local mock of the patch API serving a patched `six-1.16.0` wheel.

```sh
printf '[project]\nname = "uvp"\nversion = "0.1.0"\nrequires-python = ">=3.9"\ndependencies = ["six==1.16.0"]\n' > pyproject.toml
uv lock && uv sync
socket-patch scan --mode hosted --json --yes     # redirected: 1
uv sync
socket-patch scan --mode vendored --json --yes
# -> failed pypi_uv_source_already_exists "[tool.uv.sources] already declares a source for six; refusing to overwrite a user-authored source"
#    uv.lock still: source = { url = "http://127.0.0.1:18080/patch/pypi/six/1.16.0/<token>/<uuid>/six-1.16.0-py2.py3-none-any.whl" }
```

Root cause (shared): `crates/socket-patch-core/src/patch/redirect/takeover.rs:79` `redirect_revert_supported` only covers cargo, npm and golang, so the vendored run never reverts the hosted redirect for `pkg:pypi/`.

Not yet checked for uv: vendored → hosted, and lock-only hosted → vendored (on Poetry that fails `vendor_fetch_unverifiable` because the lock pins the patched wheel's hash).

Also unconfirmed for uv: on Poetry, vendored `repair` on a lock-only checkout whose committed wheel was deleted fails `vendor_artifact_unrepairable`, even though the vendor ledger's `wiring[].original` fragment keeps the pristine hash (see the Poetry ledger backlog). Worth checking on uv.lock.
