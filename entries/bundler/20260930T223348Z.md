[agent] 2026-09-30: Bundler (RubyGems) bug-hunt run

**Tested:** main `f6b7fb9` (v4.0.0, the latest release). Ruby 3.3.6 on Linux, with Bundler 4.0.17, 2.5.22, 2.4.22, 2.3.27, 2.2.33 and 1.17.3 (the last only for the `BUNDLED WITH` refusal). Main hasn't moved since run 1, so re-triage of #340 / #341 was a no-op: nothing landed that could fix them.

**Setup:** a temporary, uncommitted copy of `e2e_redirect_gem_build.rs` kept its wiremock (upstream compact index, patch registry, patches API with a `blobContent` view) alive in hold-open mode, and I drove the real CLI and bundler by hand. Every cell ended with a real `bundle install` / `bundle exec ruby -e 'require …'`.

## Cells

- **Hosted, platform-resolved gem (`vuln-gem (1.0.0-x86_64-linux)`) on a CHECKSUMS-less lock (backlog 1), Bundler 4.0.17:** pass (no bug). The redirect writes the Gemfile source block. The next unfrozen install drops the locked platform spec ("possibly been yanked… ignoring") and installs the patched ruby-platform gem: `PATCHED` loads. The platform switch is deliberate. With a CHECKSUMS lock, `redirect_gem_platform_unsupported` fails closed.
- **Agent + `setup` plugin, `Gemfile`: setup → get → install → `bundle pristine` → fresh clone → `setup --remove`:**
  - 2.5.22 / 4.0.17: all pass (the remove is byte-exact).
  - 2.2.33 / 2.3.27 / 2.4.22: **fail → #389.** `bundle pristine` reverts the patch and no hook fires. The patch comes back at the next `bundle install`, and `setup --check` flags `not applied on disk`. The root cause is on Bundler's side: before 2.5, pristine uses `GemInstaller#install_from_spec`, which never calls `Plugin.hook`.
- **Agent + `setup` plugin, `gems.rb`, 4.0.17:** pass (install, pristine, fresh clone).
- **`setup` 1.x refusal:** pass. A lock with `BUNDLED WITH 1.17.3` makes `setup` exit 1 with the floor message, `setup --check` exit 1 on a hand-wired 1.x project, and the refusal still fires on a CRLF lock. With no lock, the machine bundler (4.0.17) is probed, as intended.
- **Vendored, `gems.rb` only (backlog 2):** pass (documented refusal). With a plain ruby-platform install the error is the clear `no Gemfile at …/Gemfile`. Run 1's odd `package_not_installed` reason came from its platform/mock setup, not the product.
- **`BUNDLE_GEMFILE: "Gemfile.next"` in `.bundle/config` (dual boot), hosted + in-run VEX, and `setup`, 4.0.17:** **fail → #390.** Both wire `Gemfile`. The scan reports success with no warnings and attests `not_affected`, `setup --check` exits 0, and bundler loads `Gemfile.next` and runs `VULNERABLE` code. The post-install `vex` correctly refuses (`not_applied`).
- **macOS / Windows:** untested. Both new defects are OS-independent (Bundler's own code path in #389, manifest selection in #390), so I spent no probe branches.

## False positives ruled out

- `setup --json` reports `"packageManager": "npm"` on a Bundler-only project. CLI_CONTRACT documents this ("defaults to npm, only meaningful when npm files were found").
- Bundler 1.17.3 on Ruby 3.3 can't resolve against the mock compact index. That's a harness limit, so I tested the 1.x refusal through `BUNDLED WITH`.
