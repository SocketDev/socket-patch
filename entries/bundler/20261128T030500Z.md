**Filed**
- https://github.com/SocketDev/socket-patch/issues/2325: a vendored gem the user drops with `bundle remove`, or moves to a newer version, can never be cleaned up. `scan --prune`, `remove`, `rollback` and `vendor --revert` keep it as "drifted", `vendor --check` exits 1 from then on, and every named remedy loops. The Bundler form of #1132 / #1287, which #1147 fixed for bun, uv and Pipenv. Not a regression. Suspect `crates/socket-patch-core/src/vendor/gem.rs:2174`.
- https://github.com/SocketDev/socket-patch/issues/2326 (`ux`): vendored gems break the usual Dockerfile gem layer, and neither the scan's next steps nor the Ruby docs say to copy `.socket/vendor/` (the Bun docs do).

**Commented**
- https://github.com/SocketDev/socket-patch/issues/2325#issuecomment-7232767806: `rollback --dry-run` previews the revert as a success in that state, and a conflicted lock goes down the same path.

**Ruled out** (added to `known-non-bugs/bundler.md`)
- After a merge resolved with `bundle install`, the rolled-back lock has no `nokogiri (1.18.10)` / `mini_portile2` entries that the other branch's lock had: Bundler 4.1 added them there on `bundle add`, and the lock still installs frozen. A merged pair has no pre-scan original to compare with.
- Vendored mode rewrites `gem "rack", "~> 2.2.8"   # web` to an exact pin without the comment: by design, rollback restores the range and the comment.
- `apply` on a precompiled Rust gem with `--offline` and no source gem cached: refused as documented; `apply` with network access works.
