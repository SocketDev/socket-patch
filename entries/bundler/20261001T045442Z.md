## Cells (global mode, maintainer checklist)
Probe run: https://github.com/SocketDev/socket-patch/actions/runs/36816092864 (ubuntu, macos and windows × Ruby 2.7 / 3.3 / 3.4).
1. `scan -g` report: **pass** on Linux and macOS (finds the global colorize, exit 0; `SOCKET_GLOBAL=1` behaves the same). **Fail on Windows → #421**: `scannedPackages: 0` on 3.3 / 3.4, and only the `~/.gem` user copy on 2.7.
2. `-g` from inside a Bundler project with `vendor/bundle`: **pass**. Project gems don't leak into `-g`, and a scan without `-g` stays on the project stores.
3. `scan -g --mode hosted` and `--global-prefix … --mode hosted`: **pass** (exit 2, loud message, nothing written), on all 9 CI cells too.
4. `get -g` / `apply -g` / `rollback -g`: **pass** on Linux and macOS (both the gemdir and user-install copies are patched; rollback is byte-exact; re-apply is idempotent). **Fail on Windows → #421**: not found on 3.3 / 3.4; on 2.7 the system copy is missed. `vex -g` refuses correctly when the only copy is reverted, but **fails with multiple homes → #420**: it attests `not_affected` while Ruby loads an unpatched `--user-install` / `GEM_PATH` copy. That reproduced on all six Linux/macOS cells, and also with plain `vex` in a Bundler project on system gems.
5. `--global-prefix`: **pass** when given the `…/gems` leaf dir (all OSes). Given the gem home itself (`gem env gemdir`), it scans 0 packages with no hint. That's consistent with the "packages root" convention (`node_modules`, `site-packages`), so I didn't file it; see Known non-bugs.
6. Non-writable global gem dir (non-root user, root-owned rbenv gem dir, Linux): **pass**. `get -g` exits 1 with `Permission denied`.
