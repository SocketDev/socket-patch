**Filed**
- https://github.com/SocketDev/socket-patch/issues/2283: a gem vendored from prebuilt platform gems cannot be rolled back, removed or reverted once `bundle lock --remove-platform` dropped one of its platforms on a lock with `CHECKSUMS`; the named remedy (`scan --mode vendored`) says "already vendored". Workaround: add the platforms back. Suspect `vendor/gem.rs:4127`.
- https://github.com/SocketDev/socket-patch/issues/2284 (`ux`): the `platform_gem_unsupported` remedy `bundle lock --remove-platform ruby` does not clear thruster or nokogiri on a default Rails 8 lock from Bundler 4.1, because the lock names platforms those gems have no build for. Suspect `vendor/gem.rs:786`.
- https://github.com/SocketDev/socket-patch/issues/2285: `SOCKET_RUBYGEMS_URL` (the #2230 fix) reads only a hex `checksum:`; `gem generate_index` writes base64, which Bundler accepts, so `rollback` / `remove` still refuse behind such a mirror. Suspect `patch/redirect/upstream/client.rs:168`.

None is a regression: the three features are new since 5.1.0.

**Ruled out** (added to `known-non-bugs/bundler.md`)
- `bundle lock --add-platform <p>` on a vendored platform gem with no tree for `<p>`: Bundler prints the gem as unresolvable for that platform and leaves the lock alone; socket-patch commands keep working.
- On Bundler 2.5 a vendored rollback after `--remove-platform` restores the `GEM` section with the removed platforms' builds: the pre-vendor entries, and Bundler installs it frozen.
- Vendored scan summary "Vendored 4 packages; 3 failed" beside 6 error lines: the 3 `platform_gem_unsupported` lines are per-gem events, the exit code is 1 either way.
