[agent] 2026-09-30: Bundler (RubyGems) bug-hunt run

This is the first run, so the ledger started empty and there were no `pm:bundler` issues to re-triage.

**Tested:** main `f6b7fb9` (CLI reports 4.0.0; latest release 4.0.0). Ruby 3.3.6 with Bundler 4.0.9 and 2.4.22 (also installed: 2.5.22, 2.6.9). Linux only.

**Setup:** the sandbox can't reach the Socket patch API. I used a temporary, uncommitted copy of `crates/socket-patch-cli/tests/e2e_redirect_gem_build.rs`. It keeps its wiremock (upstream compact index, patch registry, patches API) alive and takes the fixture Gemfile from an env var. For vendored runs I added a small stub `patches/view/<uuid>` returning `blobContent`. Every cell ended with a real `bundle install` on a fresh checkout and a byte/require check of the installed gem.

## Cells

- **Hosted, multi-line `gem "x",` ↵ `require: false`:** **fail → #340.** The Gemfile no longer parses (bundler exit 4), while the scan reports exit 0 / `redirected: 1` and the in-run VEX says `not_affected`. Failed on 4.0.9 with a CHECKSUMS lock, 4.0.9 without CHECKSUMS, and 2.4.22.
- **Hosted, `gem "x" if …` modifier:** **fail → #340.** The condition is silently dropped (bundler 4.0.9).
- **Hosted, decl inside `group :development, :test do` with a version constraint + `require: false`:** pass. Patched bytes installed; the block is dedented, which is cosmetic.
- **Hosted, stale-install guard** (`redirect_gem_stale_install`) with `BUNDLE_PATH` in the local `.bundle/config`, as an env var only, or in the global `~/.bundle/config` (absolute): pass.
- **Hosted `rollback`:** restored the Gemfile byte-exact (single-line decl): pass.
- **Vendored (`get --mode vendored --vendor-source build`), twin `gems.rb` + `Gemfile`:** **fail → #341.** Only `Gemfile`/`Gemfile.lock` are wired. Bundler reads `gems.rb` and installs upstream bytes, yet `vex` attests `not_affected (vendored)`. Failed on 4.0.9 unfrozen and 2.4.22 `--frozen`.
- **Vendored, `gems.rb` only:** no write, exit 1 (`package_not_installed` / `vendor_fetch_unverifiable`). This is the documented "cannot vendor yet", but the refusal reason is odd, so it's on the backlog.
- **macOS / Windows:** untested. Both defects are OS-independent text/file-selection logic, so I spent no probe branches this run.

## False positives ruled out

- `vendor_fetch_failed` / `no_local_source` on the first vendored attempt came from my mock (no artifact route), not a product bug. Use `--vendor-source build` plus a view stub with `blobContent`.
- `bundle install --deployment` exit 15 on Bundler 4 is the removed flag, not socket-patch.
