### Issues
- Filed **#1101**: a hosted `scan` / `get <uuid>` or vendored `scan` run from a Bun workspace member that holds a stray `bun.lock` / `bun.lockb` pins or vendors that lock. Bun never reads it, because it installs members from the root lock, even when `bun install` runs in the member. The run exits 0 with `success`, fresh frozen installs are unpatched, and `vex` from the member attests `not_affected` (hoisted, or a lockfile-only checkout). Reproduced on 1.2.23, 1.3.9 and 1.4.2 × text / lockb × hoisted / isolated, with 1.4.2 hoisted ×2. PR #1095 (for npm's #1094) explicitly keeps the Bun shortcut, and its head still reproduces. 4.0.0 behaves the same, so it isn't a regression.
- Commented on **#1097**: Bun 1.1.39–1.2.23 ignore `!` workspace patterns, and 1.3.0+ honour them. With `["packages/*", "!packages/a"]` on 1.2.23 (isolated), hosted `scan` and `get` from `packages/a` exit 0 with `redirected: 0`, while Bun installs `a` from the root lock. A fix that keys on the lock type can't handle Bun, but the root `bun.lock` `workspaces` map can. Bun rejects extglobs outright.
