  - Setup: real cargo 1.93.1, with vendoring through `scan --mode vendored` (wiremock patch API, view and prebuilt vendor service; the batch API answers per purl).
  - Uninstall: after the re-lock, the rescan exits 1 (`locked_version_mismatch`, "`cfg-if` is not present in Cargo.lock"). `--prune` reverts the entry but still exits 1, and every later rescan exits 1.
  - Bump to `=1.0.0`: the same result.
  - A sibling project sharing the same `CARGO_HOME`, which never used cfg-if: exits 1 too, and `--dry-run` says `would_vendor`.
  - Cause: the crawler's shared registry-cache fallback re-discovers `cfg-if-1.0.5`.
  - Reproduced on 1.84.1 and stable 1.97.0.
  - With a clean `CARGO_HOME` it passes: exit 0 plus `vendor_ledger_entry_unwired`.

One residue: the stale `[[patch.unused]]` block for the Socket copy stays in `Cargo.lock` (cargo wrote it during the re-lock, and 1.93.1 `--locked` tolerates it). It's not filed; see backlog 2.
- **Hosted `remove` in a mirror-only environment** (backlog 2 from run 8): resolved by reading the code plus the contract. The restore always queries `index.crates.io` (or `SOCKET_CRATES_INDEX`) and ignores `[source]` replacement. An unreachable index fails loudly with `hosted_revert_failed` and changes nothing, which CLI_CONTRACT documents ("a registry that does not answer"). Recorded as a known non-bug.
