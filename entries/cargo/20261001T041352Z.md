## Cells: global mode (maintainer request, Linux only)

- `scan -g` report-only (no `--mode`), from outside a project: pass. It finds exactly the patched global crate. `--json` is correct.
- `scan -g` from inside a project: pass. The project's lockfile-only crates don't leak in, so it scans the global location only.
- `scan -g --mode hosted`, `scan --global-prefix <dir> --mode hosted` and `SOCKET_GLOBAL=1 scan --mode hosted`: pass. Each exits 2 with "global installs have no project lockfile to redirect" and writes nothing.
- `scan -g --mode agent`, `get <purl> -g` (defaults to agent) and `apply -g`: pass. The registry-cache copy is patched, and `cargo run --locked --offline` links the patched symbol.
- `rollback -g` and `--global-prefix`: pass. The restore is byte-exact.
- `vex -g --product …`: pass. It attests only when the patch is applied, and a reset copy is omitted as `not_applied`. Without `--product` it exits 2 asking for one, which is correct.
- `--global-prefix` / `SOCKET_GLOBAL_PREFIX` with a space-and-unicode CARGO_HOME path: pass.
- Unwritable global dir (root-owned CARGO_HOME, CLI run as `nobody` via setpriv): pass. It exits 1 with "Permission denied (os error 13)" and `partial_failure`.
- Several index dirs under `-g`: **fail, #339**.

## Cells: other

- **Agent `cargo vendor` tree: apply, `--frozen --offline` build, rollback.** Sources are restored exactly, but `.cargo-checksum.json` comes back pretty-printed instead of cargo's compact bytes, so a committed `vendor/` stays dirty. **Fail → #416** (new, low severity). Release 4.0.0 behaves the same, so it isn't a regression.
- **Hosted scan with `--cwd` at a workspace member.** It rewrites the member as a lockless project, leaves the root lock alone, and every workspace build breaks while the scan reports success. **Fail → #417** (new). Reproduced on 1.93.1 and 1.97.0.
- **Hosted `remove` / `rollback` with the crates.io index unreachable** (`SOCKET_CRATES_INDEX` pointed at a dead port): pass. It fails loudly with `hosted_revert_failed`, nothing is half-written, and `cargo fetch --locked` still works.
- **Hosted with an unrelated `[registries.other]` + `[net]` in `.cargo/config.toml`, and with a CRLF `.cargo/config.toml`:** pass. That covers the full scan → fresh `--locked` build → vex → byte-exact remove chain.

## False positives and observations (not filed)

- A local (non-`-g`) agent scan in a Cargo project crawls the whole shared `registry/src`. It patches crates the project's `Cargo.lock` doesn't contain, records them in the project manifest, and `vex --product <project>` then lists them as subcomponents. The crawler doc and CLI_CONTRACT both describe the registry-cache fallback ("wherever the crawler finds it"), so this looks like a design choice, and I didn't file it. It needs a maintainer call on whether agent scope (and VEX) should be intersected with `Cargo.lock`.
- `-g` patches the registry *source* cache, not binaries already built by `cargo install` in `$CARGO_HOME/bin`. That's inherent to cargo and undocumented, but not a defect.
- The Known non-bugs entries about `setup.manual` and `ecosystem_not_setup` are obsolete in v5 (`setup` was removed, and agent-mode `vex` now attests cargo directly). I've rewritten them in the state file.
