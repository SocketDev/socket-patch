**Harness:** I rebuilt it from scratch.
- `mkpatch.py <name> <ver> <file> <uuid> <out>` installs the package, builds a patched tgz (a marker prepended to `<file>`), bootstraps `yarnBerry10c0` with a real `resolutions: file:` install, and reads the original checksum from the registry lock. Never patch `package.json`: the marker breaks the JSON and the bootstrap fails.
- A single Python mock serves batch, by-package, `patches/package`, view (with blob contents), `/upstream/npm/<uuid>.json`, the tarball route and a `/registry/` passthrough. It logs each request's `Authorization` header.
- Standalone `vex` against the mock needs `--patch-server-url <mock>` plus the API flags. Without them it reports "nothing to attest" or `record_unavailable`, which is a harness artifact, not a bug.
- Don't wait on the build with `until …; pgrep -f "cargo build"`: the pattern matches its own shell.

### Cells (Linux, node-modules linker, yarn 4.18.1 unless noted)
- Hosted, two versions of one package both patched (root `^1.3.0` and member `1.2.0`, two uuids): both are pinned, the fresh immutable install patches both, and the re-scan is idempotent. `rollback <purl>` unpins only that version, and the other stays patched in a fresh install. A full rollback is byte-exact. **pass**
- Hosted on a user `patch:` descriptor in `dependencies`: refused with `redirect_yarn_berry_unsupported_protocol` plus `shared_descriptor`, nothing written. **pass**. Agent mode on the same package patches `index.js` and keeps the user's README hunk; vex gives `not_affected`, and rollback restores it. **pass**
- Hosted `debug@4.3.4` (has `dependencies` plus `peerDependenciesMeta`): fresh immutable patched, rollback byte-exact. **pass**
- Vendored, then `yarn add is-number`, `yarn up debug`, `yarn dedupe`: the pin survives, and vex gives `not_affected`. `vendor --revert` afterwards keeps the user's `is-number` and leaves an immutable-clean lock. **pass**
- Hosted with `npmAlwaysAuth: true` (global and scoped) plus `YARN_NPM_AUTH_TOKEN` in hardened mode: the patch host received no `Authorization` header, and the install is patched. **pass** (backlog 6)
- **Platform-conditional entries (`conditions: os=…`): fail, filed #697.** Vendored misplaces `checksum:` after `conditions:` on every conditional entry. Hosted inserts it before `dependencies:` when the original entry has none. Every `yarn install --immutable` then fails YN0028 on yarn 4.0.2, 4.6.0, 4.12.0 and 4.18.1. Release 4.0.0 behaves the same, so it isn't a regression. Hosted passes the esbuild cells (no deps) and the `supportedArchitectures` darwin cell.
- Hosted rollback of a conditional entry that had no checksum keeps the inserted `checksum:` line, so it isn't byte-exact. Yarn accepts it under immutable, and its next mutable install strips it. I noted it in #697; it isn't filed separately.
- **`yarn remove` of a vendored package, then `rollback`:** exit 1 on every run (`vendor_lock_entry_drifted` + `vendor_artifact_kept`), and `remove` exits 1 too. `vendor --revert` exits 0 as a no-op, and `vendor --check` says OK (4.12.0, 4.18.1). This is the same bug as #665; I commented there with the Berry evidence. #689's Berry hook has no Berry test.
- **Symlinked `yarn.lock` or `package.json`:** hosted refuses both with `redirect_symlinked_file_unsupported` and writes nothing. Vendored (dry-run too) exits 0 and replaces the link with a regular file, leaving the target unpatched, and rollback doesn't restore the link. This is #627's root cause (group commit); I commented there.
