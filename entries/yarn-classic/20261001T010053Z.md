## False positives ruled out / findings that aren't bugs
- **Why CI's yarn 1.0.2 / 1.6.0 vendored cells "fail":** I bisected by Node version. Yarn 1.0.2 and 1.6.0 exit 0 and install **nothing** for a `file:` tarball lock entry on Node 10.24.1, 14.21.3, 16.20.2 and 22. Yarn 1.7.0 installs it on all four. The cause is in yarn ≤ 1.6, not in socket-patch and not in Node, which matches CI's comment ("1.7.0 first vendored-capable"). socket-patch can't tell which yarn will run the install from the lock (1.6 and 1.9 locks look the same). This limitation appears only in CI comments, not in docs/ecosystems.md, so a docs note would help. Not filed.
- **Running scan from a workspace member dir** (`cd packages/b`): vendored fails cleanly (`vendor_lockfile_missing`, exit 1). Hosted exits 0 with `redirected: 0` and `redirect_npm_no_lockfile` ("no package-lock.json / npm-shrinkwrap.json present"), whose wording ignores the root `yarn.lock`. That matches the documented "hosted refusals exit 0 + warning" stance, so it's a UX note, not filed.
- **Hosted `vex` on a lock-only checkout said `package_not_found`.** This is documented (CLI_CONTRACT "Patch hosts"): my mock host isn't Socket's patch server. With `--patch-server-url` it attests `(redirected)`.
- The probe's Windows `Couldn't find the binary git` was #363 itself, not a missing git: the control install of the same dep passed in the same job.
