## Cells
- **Vendored workspaces, installs run from a member dir → fail, filed #691.** `cd b && yarn install --frozen-lockfile`, `yarn --cwd b install` and `yarn workspace b add` all fail on a cold cache with `Tarball is not in network` (yarn resolves `file:./.socket/vendor/…` against the cwd). Root installs pass, and so do warm-cache member installs. Reproduced on Linux / macOS / Windows × 1.7.0 / 1.10.1 / 1.22.22. Control: the pre-vendor registry lock passes from the member dir. A hand-written `file:` tarball dep fails the same way (the root cause is yarn's handling, but socket-patch introduces the entry, with no warning and nothing in the docs).
- **Yarn merging a second range into the vendored block (`left-pad@^1.1.0, left-pad@^1.3.0:`) → fail, filed #692.** Rollback ×2 exits 1 ("no longer exists"), and the lock stays wired. `remove` exits 1, `vendor --revert` exits 0 as a no-op, and re-vendoring says `already_vendored` without re-keying, so the printed remedy loops. Linux 1.7.0 / 1.10.1 / 1.22.22.
- `yarn add left-pad@^1.3.0` at a non-workspace root after vendoring (`^1.1.0` → `^1.3.0`): yarn re-resolves the block from the registry (unpatched). That's yarn's own behaviour; the rollback that follows is the #665 shape. Not filed again.
- Backlog item 4 (`yarn upgrade` to another version): the block is re-keyed, which is the #665 shape (covered by #689).
