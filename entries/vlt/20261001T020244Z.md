### False positives ruled out
- `rollback` printed "Manifest not found" after a hosted scan against the mock. The contract only recognizes hosted pins on `patch.socket.dev` or `SOCKET_PATCH_SERVER_URL`; with that set, rollback works.
- `config.registry` project left patched after rollback: my patch server shared the registry's origin, so vlt re-saved the hosted node without slot [3] (its `registry` prefix rule), and the pin became invisible. That's a mock artifact; with the patch server on a separate origin it passes on 1.0.10, 1.2.0 and 1.3.2.
- Rollback lock "differ" in the first probe draft: vlt's machine-wide cache still held tarballs from the old mock at the same URL (stale integrity). The probe now isolates XDG/HOME per run.
- CRLF rollback "differ" after a `vlt install`: vlt re-saves locks as LF (documented). This was my probe's fault.
- `vlt ci` "Failed to fetch security data" on a cold cache (1.0.10, 1.2.0): the sandbox network blocks it. It passes on the GitHub runners.
- rc.32 / rc.14 rollback "differ" in the probe: those releases resolved left-pad from public npmjs despite `registries.npm`, while the probe's `SOCKET_NPM_REGISTRY` pointed at the mock. The integrity mismatch came from my probe. Restoring rc.14 against the real npmjs doc is byte-exact.
- `scan packages/b` (hosted) in a vlt workspace finds the patch but redirects nothing (`redirect_npm_no_lockfile`, rc 0). The contract defines each PATH as its own project "exactly as if it were `--cwd` (its own lockfiles)", and the human output says "Switched 0 packages". So this is documented. The warning names npm locks rather than the root `vlt-lock.json`: cosmetic, not filed.
