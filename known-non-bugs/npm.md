# npm known non-bugs and documented limitations

One line each. Moved from state/npm.md on 2026-11-26; search with git grep.

- A hosted re-run that finds every pin already in place reports each one as an `applied` event (`summary.applied` counts it) with `rewrittenFiles: []` and `rollout.counts.already`. That's deliberate (`record_hosted_events` maps every confirmed pin to `applied`), the human text says "already on hosted patches; nothing to rewrite", and it isn't specific to npm (run 65).
- npm doesn't install the dependencies of a workspace member outside the project root (`"workspaces": ["../shared"]`), the same as a `file:` link target there, so there's no copy to patch (npm 10.9.9, run 65).
- npm drops the last hosted pin itself (`npm install left-pad@<other>`, `npm update`): the `allow-remote=all` line hosted mode created stays in `.npmrc`, and `rollback` / `remove` then exit 1 `manifest_not_found` (the same as a plain project). That follows from v5 keeping no hosted provenance outside the lock (run 64, npm 12.2.1).
- A dependency declared as a remote tarball URL on the registry host has a lock entry identical to a registry one; hosted skips it and vendored refuses it, naming the dependent spec. Correct (npm installs it from that spec) (run 62).
- `package-lock=false` + vendored (run 61, npm 10.9.9 / 12.2.1): after a plain `npm install` (which ignores the lock) `vex` attests from the committed artifact with the documented `vendored_tree_out_of_sync` warning; `npm ci` still installs the patched bytes. Same reasoning as the hosted entry below.
- A workspace member (or any dir) carrying a signed CACHEDIR.TAG is pruned from the crawl: documented in docs/ecosystems.md ("prunes every directory that carries a CACHEDIR.TAG").
- npm 6.14.18 with a lockfileVersion 1 hosted pin installs the patched bytes when the npm cache already holds the patched tarball (cacache lookup by integrity); with a cold cache it fails EINTEGRITY as documented (`redirect_npm_legacy_client`). Not a bug (run 60).
- Hosted `rollback` / `remove` of a package-lock pin reads the version document only from the default registry (npmjs or `SOCKET_NPM_REGISTRY`), not from a project `.npmrc` `registry=` / `@scope:registry=`. A package only that registry serves refuses `hosted_restore_refused` with a `git checkout` remedy and an untouched lock. Deliberate (#918 kept `fetch_dists` for package-lock; #1130 tracks the restore design) (run 59).
- npm does not install the dependencies of a `file:` link target outside the project root, so there's no out-of-root copy to patch (npm 10.9.4 / 12.2.1, run 59).
- Hosted `rollback` against a package the upstream registry (`registry.npmjs.org` or `SOCKET_NPM_REGISTRY`) doesn't serve fails `hosted_restore_refused` with a `git checkout` remedy; a pre-existing project `.npmrc` keeps the `allow-remote=all` line hosted mode added (documented `npm_allow_remote_left`) (run 58).
- A project `.npmrc` that is a symlink is never written through: the hosted run pins the lock, leaves the link and its target untouched, and warns `redirect_npm_allow_remote` ("is a symbolic link … add `allow-remote=all` to it yourself"). npm 12 `npm ci` then fails closed with EALLOWREMOTE. Deliberate (run 56).
- `npm update` (and `npm install <pkg>@<same version>`) re-resolves a hosted pin to the registry `resolved`. That's npm behaviour: socket-patch keeps no hosted state outside the lock, so `vex` refuses (exit 2, nothing to attest) and a re-scan re-pins (run 56).
- A workspace member's own `bundleDependencies` gets no `inBundle` flag in the lock (npm 8 / 10 / 12), so its deps are ordinary entries (run 56).
- Hosted lock-only `vex` attests a pin whose package isn't installed on this platform (an `os`-restricted optional dep) or by a workspace-scoped `npm ci -w`. Documented: installed copies are verified "when available" (run 55).
- `rm -rf node_modules/<pkg> && npm install` with the `.bin/<name>` link still present: npm skips `fixBin` (`link-gently` SKIP) and leaves a CRLF bin that exits 127. socket-patch writing the LF form there (so rollback isn't byte-exact against npm's broken bytes) is acceptable (run 54).
- A bundled dep's CRLF bin with the default `rebuild-bundle=true`: npm runs `fixBin` on it (LF), and main's LF writes and byte-exact rollback are correct (run 54, npm 6 / 10 / 12).
- A registry package that declares bins only via `directories.bin`: the packument carries the expanded `bin`, so npm links it and runs `fixBin`, and main's LF form is correct (run 53). Only non-registry installs hit #1804.
- A Ctrl-C or kill during the eject's artifact *download* is safe: the download runs before the upstream restore, so the lock is still hosted (main `b787454`, 2026-10-28T13Z).
- After vendoring, `npm shrinkwrap` renames package-lock.json to npm-shrinkwrap.json. `vendor --revert` then refuses with advice that names the rename ("was the wired lockfile renamed — e.g. by `npm shrinkwrap`"), and `vex` omits the patches (`vex_npm_shrinkwrap_only`, documented). Hosted `rollback` restores the renamed lock (npm 10.9.4, 2026-10-28T07Z).
- `repair` of a deleted `<uuid>/` dir restores the tarball, `.gitignore` and `.gitattributes`, but not the `socket-patch.vendor.json` marker. The marker is documented as informational ("never a trust input"), and `repair` is documented to restore the ignore/attributes pair; `vendor --check` and a fresh clone's `npm ci` pass (npm 10.9.4 dual lock + workspace + `*.tgz` ignore, 2026-10-28T07Z).
- patch-package treats subdirectories of `patches/` as nested package paths (`patches/sub/x+1.0.0.patch` targets `node_modules/sub/x`), so the non-recursive `patches/` read in `user_patches.rs` is correct (patch-package 8.0.0, 2026-10-28T07Z).
- With a warm npm cache holding the patched tarball, npm 6.14.18 `npm ci` on a hosted v1 lock installs the patched bytes (cacache hit by integrity) rather than the EINTEGRITY the `redirect_npm_lockfile_v1` warning predicts. Harmless (2026-10-28T07Z).
- A wet `vendor` eject's `--json` lists each package as `applied` plus a `skipped` `vendor_prebuilt_downloaded` advisory event; that's the documented advisory pattern (2026-10-28T07Z).
- A workspace member's own `bundleDependencies` copy (`packages/a/node_modules/ms`, `inBundle: true` in the root lock) is neither pinned nor reported by hosted / vendored. npm itself never reinstalls such a copy from a clean tree (`npm ci` and `npm install` after `rm -rf node_modules` both leave it absent), so no unpatched copy runs (npm 10.9.4, 2026-10-28).
